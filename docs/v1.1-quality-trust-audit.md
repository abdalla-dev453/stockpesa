# StockPesa V1.1 Quality & Trust Audit

**Review date:** 17 November 2026  
**Scope:** repository and existing QA report review. No device profiling or live API/database exercise was available during this review.

## Current state

- **Brand:** emerald/forest icon SVG and PNG exist, plus Android/iOS launcher artwork and an SVG splash asset path. Adaptive/monochrome Android layers, requested size exports, full wordmark, and reusable onboarding/empty-state illustrations are not present as a complete asset set.
- **Categories:** tenant-scoped CRUD and category filtering already exist. Registration did not create defaults. The mobile manager supported create/delete but not rename.
- **Alerts:** stock transitions create in-app low-stock/out-of-stock alerts with unread badge/read actions and suppress repeated unread alerts. Per-user preferences, authenticated device-token registration/revocation, a transactional push outbox, and an FCM HTTP v1 dispatcher are now implemented. Live delivery still requires platform configuration and runtime credentials.
- **Insights:** dashboard, sales summaries, top products, stock/debt reports and low-stock suggestions use tenant data. Market context, sales velocity forecasts, dead-stock/overstock analysis, and 7/30 day trend views are incomplete.
- **Navigation:** bottom navigation includes Home, Products, Sell, Stock and More; New sale is a prominent action. Product search and barcode scanning exist. Search is not global.
- **Theme:** Material light/dark themes existed and followed system mode. A persistent user choice is now available in Business settings.
- **Legal:** registration had an untethered checkbox. It now links to draft privacy/terms screens and sends an accepted version to the API, which records consent time/version. The drafts intentionally identify themselves as templates.
- **Security/release:** see the prior `qa-audit-report.md`; debug release signing, limited automated critical-flow coverage, and unverified tenant isolation remain release concerns. This review does not certify security or legal compliance.

## Priority order

1. **P1 — Release and assurance:** resolve release signing; run tenant isolation/role and critical transaction tests in a disposable environment; verify migration and signup consent behavior.
2. **P1 — Notification rollout:** configure Firebase apps, APNs and server secrets for each environment; apply migrations; then exercise preference filtering, retry/deduplication and foreground/background/terminated delivery on devices.
3. **P1 — Trust and legal:** have Kenyan counsel review the legal templates; replace operator/contact placeholders; confirm retention, processor and cross-border transfer details before release.
4. **P2 — Categories and brand:** provide defaults and rename UX (implemented in this slice); complete launcher/adaptive assets and apply them consistently to splash and empty states.
5. **P2 — Insights and speed:** measure baseline on representative devices and realistic tenant data, then add only data-supported insights and optimize measured hotspots.
6. **P2 — Navigation:** add global search only after defining a unified, permission-aware search API and preserving existing fast product/barcode paths.

## Performance baseline and targets

No numeric performance baseline can be responsibly reported without a profile/release build, representative physical Android device, and live backend/data. The earlier QA audit recorded that the Flutter toolchain/device environment was unavailable. Record cold start, dashboard/product/report load, checkout, API latency, frame timing and package size under a repeatable environment before optimizing.

Proposed targets after measurement: no sustained scroll jank on the selected mid-range device; paginated product browsing; checkout stays responsive under normal network conditions; no material regression in cold start, screen load or package size. Set numeric thresholds from the first reproducible run rather than inventing current values.

## Notification architecture proposal

Keep the current business-scoped alert inbox as the single in-app source of truth. Generate a stable event key from tenant, event type and relevant entity/state transition; persist the event and push-delivery intent transactionally; send to opted-in active device tokens after commit; record success/failure and invalidate rejected tokens. A preference belongs to a user, while each event remains tenant-scoped and role-filtered. Push taps should route to the same entity represented in-app. Daily summaries should be generated server-side so they work while the app is closed. Firebase delivery cannot be enabled until project IDs, platform configuration and server credentials are supplied.

## Remaining gates

- Representative Android/iOS build and device run.
- Firebase configuration and push lifecycle verification; failed-login alerts and delivery-status inspection remain additional improvements.
- Database migration and registration consent verification.
- Kenyan legal review and operator contact details.
- Security review of tenant, roles, session behavior and public release signing.
