# StockPesa Phase 3 manual end-to-end test

Run from a clean development database. This script covers sales, stock, credit, returns, payments, receipts, M-Pesa, reports, tenant isolation and role access. Use demo credentials from `backend/prisma/seed.ts` after seeding, or register two businesses and create the needed users/products/customers.

## Start the app

1. In `backend/.env`, set a local `DATABASE_URL`, distinct random `JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET`, `MPESA_MODE=mock`, and a long random `MPESA_CALLBACK_SECRET`.
2. Start Postgres, then run `cd backend && npm ci && npx prisma generate && npx prisma db push && npm run prisma:seed && npm run start:dev` (Node 22.22.3 or newer).
3. In another terminal start the app with `cd mobile && flutter run --dart-define=API=http://10.0.2.2:3000` for Android emulator (use your host's reachable address on a physical device).
4. Sign in as `owner@stockpesa.app` / `Demo1234!`. The seed creates 30 products, 24 historic sales, 4 roles and one credit customer. For isolated runs, use a fresh database: seeding intentionally skips when the demo owner exists.

## Checks

1. **One sale, one stock deduction.** Note the quantity for an in-stock product. Create a sale for quantity 2. The quantity must fall by exactly 2 and there must be one `sale_out` movement referencing that sale number.
2. **Atomic sale artifacts.** Inspect a completed cash sale, its sale items, payment, receipt and `sale.completed` audit record. Their IDs/references must point to the same sale. The receipt snapshot is created in the sale transaction.
3. **Rollback on failure.** Record counts of sales, payments, receipts, sale movements and audit records. Submit a sale containing one valid product followed by a product belonging to another business, or force a DB error during the request. Expect an error and no count or stock changes.
4. **Credit and customer debt.** Select a customer and choose CREDIT. The sale must have zero paid and full balance due; the customer's balance must increase by exactly that due. The sale must obey the credit limit.
5. **Payment ceiling.** On customer details, settle part of one unpaid sale. Try paying more than that sale's balance and then more than the customer's total balance; both must be rejected without changing either balance. Pay the exact remaining amount and verify both reach zero.
6. **Return quantity ceiling.** Return part of a sale, then try to return more than its remaining sold quantity. The second request must be rejected and returned quantity must not change.
7. **Return restocking choice.** Record one return with “Return accepted items to stock” checked and one with it unchecked. Both create return records and update returned quantities; only the checked one creates `return_in` movements and increases stock.
8. **Idempotency.** Send the same `POST /sales` twice with the same `Idempotency-Key` header and identical JSON body. Both responses must identify the same sale; stock decreases once. Reuse that key with a different body and expect a conflict without writes. Repeat for `POST /sales/:id/returns` and `POST /customers/:id/payments`; retries with the same key must replay without a second return movement or second payment. Stock intake/adjustment also replays by key.
9. **M-Pesa mock.** Choose MPESA in checkout. The API should create a pending payment, not count it as paid. With mock mode enabled, the mobile flow invokes the mock confirmation. Verify payment PAID, sale balance zero, customer debt reduced, receipt updated with the mock reference and a `payment.mpesa.confirmed` audit event. `POST /payments/mpesa/mock/:paymentId/confirm` is the authenticated mock trigger.
10. **Callback security.** `POST /payments/mpesa/callback` with a missing or incorrect `X-Mpesa-Signature` must return 403 and make no changes. For a pending payment, sign the exact UTF-8 canonical string `checkoutRequestId.resultCode.receiptNumber` with HMAC-SHA256 using `MPESA_CALLBACK_SECRET`, send the hex digest in `X-Mpesa-Signature`, and verify a result code 0 settles exactly once. Replaying the same signed callback returns `replayed: true`. Use a nonzero result code to verify a failed payment stays unpaid.
11. **Reports.** Run a sale with a known product cost/price, a return and a payment. `GET /reports/sales?from=...&to=...` must show net sale total, profit net of returns using unit cost, discounts and the return restocking choice, paid method totals net of refunds, and outstanding. `GET /reports/customer-debt` must equal the sum of open customer balances.
12. **Tenant and role boundaries.** Register a second business. Use its token to request the first business's sale, customer, product, stock count, alert and payment IDs; each must return not found/empty, never data. A Storekeeper must be forbidden from `POST /sales`, `GET /reports/sales`, staff changes and customer payments; a Cashier may sell but must be forbidden from owner/manager reports and stock intake.
13. **Receipt PDF.** Open a known sale in Sales History and share/print its PDF. Match business/contact, receipt number/date, customer, item names/quantities/line totals, subtotal, sale discount, tax, total, payments, paid amount, balance, returns and footer to the stored sale-time receipt snapshot. Rename a product or update the business contact/footer after the sale; the old receipt must retain its original sale-time values.
14. **Seed/report sanity.** On a fresh seed, dashboard has products, sales, low/out-of-stock counts and alerts. Sales report has 24 historical sales; stock levels equal opening stock minus seeded `sale_out` and adjustment movements. Customer balance equals the sum of its open sale balances. Products, payment methods and profit report rows must be nonzero.

For database assertions, inspect Prisma Studio (`cd backend && npx prisma studio`) or query Postgres read-only. Do not edit rows to make a check pass; reset the development database and reseed before rerunning.
